## 1. Аутентификация и авторизация

**Аутентификация** — это процесс проверки личности пользователя.

Она отвечает на вопрос:

```text
Кто ты?
```

Пример: пользователь вводит email и пароль, сервер проверяет их и понимает, что это действительно конкретный пользователь.

**Авторизация** — это процесс проверки прав пользователя.

Она отвечает на вопрос:

```text
Что тебе разрешено делать?
```

Пример: пользователь вошёл в систему, но он может редактировать и удалять только свои записи, а не записи других пользователей.

---

### В рамках проекта

| Процесс | Где реализован |
| --- | --- |
| Аутентификация | `/auth/register`, `/auth/login`, JWT, cookies |
| Авторизация | защита `/items`, проверка `owner_id` |

## 2. Соль при хешировании пароля

**Соль** — это случайная строка, которая добавляется к паролю перед хешированием.

Например, если пользователь вводит пароль:

```text
Password123
```

то фактически хешируется не только пароль, а комбинация:

```text
Password123 + random_salt
```

---

### Зачем нужна соль

Соль нужна для того, чтобы одинаковые пароли давали разные хеши.

Если два пользователя зарегистрируются с одинаковым паролем, без соли у них могли бы получиться одинаковые значения хеша. Это опасно, потому что злоумышленник сразу увидел бы, что пароли совпадают.

С уникальной солью ситуация другая:

| Пользователь | Пароль | Соль | Хеш |
| --- | --- | --- | --- |
| user1@example.com | Password123 | random_salt_1 | hash_1 |
| user2@example.com | Password123 | random_salt_2 | hash_2 |

Даже при одинаковом пароле хеши будут разными.

---

### От чего защищает соль

Соль помогает защититься от:

- радужных таблиц;
- массового сравнения одинаковых паролей;
- заранее подготовленных словарей хешей;
- быстрого анализа базы при утечке.

---

### В рамках проекта

В проекте для каждого пользователя создаётся отдельная соль:

```text
password_salt
```

А сам пароль хранится только в виде хеша:

```text
password_hash
```

Пароль в открытом виде в базе данных не сохраняется.

## 3. Структура JWT и проверка токена

JWT состоит из трёх частей:

```text
header.payload.signature
```

---

### Header

`Header` содержит информацию о типе токена и алгоритме подписи.

Пример:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

---

### Payload

`Payload` содержит данные, которые сервер помещает в токен.

Пример:

```json
{
  "sub": "1",
  "email": "test@example.com",
  "type": "access",
  "exp": 1234567890
}
```

Где:

| Поле | Значение |
| --- | --- |
| `sub` | идентификатор пользователя |
| `email` | email пользователя |
| `type` | тип токена: `access` или `refresh` |
| `exp` | время истечения токена |

---

### Signature

`Signature` — это подпись токена.

Она создаётся на основе:

```text
header + payload + secret
```

Секретный ключ хранится на сервере и не должен быть известен клиенту.

---

### Как сервер проверяет JWT

Сервер выполняет следующие действия:

1. Получает токен из cookie.
2. Разделяет токен на `header`, `payload` и `signature`.
3. С помощью секретного ключа заново вычисляет подпись.
4. Сравнивает вычисленную подпись с подписью из токена.
5. Проверяет срок действия `exp`.
6. Проверяет тип токена: `access` или `refresh`.
7. При необходимости проверяет наличие токена в базе данных.

Если подпись не совпадает или срок действия истёк, токен считается недействительным.

---

## 4. Refresh Token и Stateless Access Token

**Access Token** обычно имеет короткий срок жизни, например 15 минут.

Его можно проверять stateless, потому что вся основная информация уже находится внутри JWT:

- id пользователя;
- email;
- тип токена;
- срок действия;
- подпись.

То есть сервер может проверить Access Token без обращения к базе данных.

---

**Refresh Token** живёт дольше, например 7 дней.

Он используется для получения новой пары токенов. Из-за долгого срока жизни он опаснее: если его украдут, злоумышленник сможет дольше поддерживать сессию.

Поэтому Refresh Token рекомендуется хранить в базе данных.

---

### Зачем хранить Refresh Token в БД

Хранение Refresh Token на сервере позволяет:

- реализовать logout;
- реализовать logout-all;
- отзывать конкретную сессию;
- блокировать украденный refresh token;
- отслеживать активные сессии пользователя.

---

### В рамках проекта

В проекте в базе данных сохраняются хеши и Access Token, и Refresh Token:

```text
auth_tokens.token_hash
```

Это позволяет отзывать токены и проверять их активность.

## 5. HttpOnly cookies и LocalStorage

`HttpOnly` cookies — это cookies, к которым нельзя получить доступ через JavaScript.

То есть такой код не сможет прочитать токен:

```js
document.cookie
```

если cookie имеет флаг:

```text
HttpOnly
```

---

### Почему LocalStorage менее безопасен

Если токен хранится в `LocalStorage`, его можно прочитать через JavaScript:

```js
localStorage.getItem("token")
```

При XSS-атаке вредоносный скрипт может украсть токен из `LocalStorage`.

---

### Преимущества HttpOnly cookies

| Преимущество | Описание |
| --- | --- |
| Защита от кражи через JS | JavaScript не может прочитать токен |
| Автоматическая отправка | Браузер сам отправляет cookies на сервер |
| Поддержка `SameSite` | Можно снизить риск CSRF |
| Поддержка `Secure` | Можно разрешить передачу только по HTTPS |

---

### Недостаток cookies

Cookies могут быть подвержены CSRF-атакам, поэтому нужно использовать:

- `SameSite`;
- проверку `state` в OAuth;
- HTTPS;
- дополнительные CSRF-механизмы при необходимости.

---

## 6. Назначение эндпоинта `/whoami`

При использовании `HttpOnly` cookies фронтенд не может напрямую прочитать токен.

То есть клиентская часть не может просто проверить:

```js
document.cookie
```

и узнать, есть ли там `access_token`.

---

### Зачем нужен `/whoami`

Эндпоинт:

```text
GET /auth/whoami
```

нужен для проверки текущей авторизации пользователя.

Фронтенд отправляет запрос на сервер, браузер автоматически прикладывает cookies, а сервер проверяет токен и возвращает профиль пользователя.

---

### Возможные ответы

Если пользователь авторизован:

```json
{
  "message": "User is authenticated",
  "user": {
    "id": 1,
    "email": "test@example.com"
  }
}
```

Если пользователь не авторизован:

```json
{
  "detail": "Not authenticated"
}
```

---

### В рамках проекта

`/auth/whoami` используется для проверки текущей сессии по `access_token` из `HttpOnly` cookie.

---

## 7. Параметр `state` в OAuth 2.0

`state` — это случайная строка, которая используется для защиты OAuth-процесса от CSRF-атак.

---

### Как работает `state`

1. Backend генерирует случайный `state`.
2. Сохраняет его, например в cookie.
3. Отправляет пользователя на OAuth-провайдера вместе с этим `state`.
4. OAuth-провайдер после авторизации возвращает пользователя обратно с тем же `state`.
5. Backend сравнивает полученный `state` с сохранённым.
6. Если значения не совпадают, запрос отклоняется.

---

### Что будет без `state`

Без проверки `state` злоумышленник может попытаться:

- подставить чужой authorization code;
- навязать пользователю чужую OAuth-сессию;
- выполнить CSRF-атаку на OAuth callback.

---

### В рамках проекта

При входе через Yandex ID backend создаёт:

```text
oauth_state
```

Сохраняет его в cookie и проверяет на callback-эндпоинте:

```text
/auth/oauth/yandex/callback
```

Если `state` не совпадает, сервер возвращает ошибку авторизации.

---

## 8. Authorization Code Grant

**Authorization Code Grant** — это OAuth 2.0 поток, при котором приложение сначала получает временный authorization code, а затем обменивает его на access token провайдера.

---

### Шаги потока

1. Пользователь нажимает «Войти через Яндекс».
2. Backend генерирует `state`.
3. Backend формирует ссылку авторизации.
4. Пользователь перенаправляется на Яндекс.
5. Пользователь входит в аккаунт и подтверждает доступ.
6. Яндекс возвращает пользователя на callback URL.
7. В callback приходят параметры `code` и `state`.
8. Backend проверяет `state`.
9. Backend отправляет `code`, `client_id` и `client_secret` в Яндекс.
10. Яндекс возвращает access token провайдера.
11. Backend запрашивает профиль пользователя у Яндекса.
12. Backend ищет пользователя в локальной БД или создаёт нового.
13. Backend создаёт собственные JWT access/refresh токены.
14. Backend устанавливает токены в `HttpOnly` cookies.
15. Пользователь считается авторизованным в локальном приложении.

---

### Важно

Токен Яндекса используется только для получения данных пользователя у Яндекса.

Для работы в локальном приложении backend выдаёт свои собственные токены:

```text
access_token
refresh_token
```

## 9. Разница между `/logout` и `/logout-all`

`/logout` завершает только текущую сессию.

Он берёт текущие токены из cookies:

```text
access_token
refresh_token
```

затем находит их хеши в базе данных и помечает их как отозванные:

```text
revoked = true
```

После этого cookies удаляются у клиента.

---

`/logout-all` завершает все сессии пользователя.

Он определяет текущего пользователя и отзывает все его активные токены:

```text
WHERE user_id = current_user.id
```

---

### Сравнение

| Эндпоинт | Что делает |
| --- | --- |
| `/auth/logout` | Завершает текущую сессию |
| `/auth/logout-all` | Завершает все сессии пользователя |

---

### Пример

Если пользователь вошёл с ноутбука и телефона:

- `/logout` на ноутбуке завершит только сессию ноутбука;
- `/logout-all` завершит сессии и на ноутбуке, и на телефоне.

## 10. Защита от CSRF в OAuth

CSRF в OAuth предотвращается с помощью параметра:

```text
state
```

---

### Реализация защиты

1. Сервер генерирует случайный `state`.
2. Сохраняет его в cookie.
3. Передаёт `state` в URL авторизации.
4. Получает `state` обратно на callback.
5. Сравнивает полученное значение с сохранённым.
6. Если значения не совпадают, callback отклоняется.

---

### Дополнительные меры

Для усиления защиты можно использовать:

- `SameSite=Lax` или `SameSite=Strict`;
- короткое время жизни `state`;
- HTTPS;
- запрет повторного использования `state`;
- проверку redirect URI.

---

### В рамках проекта

В проекте при OAuth через Yandex ID используется:

```text
oauth_state
```

Он сохраняется в cookie и проверяется при возврате пользователя от Яндекса.

## 11. Безопасные и небезопасные данные профиля

При возврате профиля пользователя важно не отправлять клиенту чувствительные данные.

---

### Безопасно возвращать

| Данные | Комментарий |
| --- | --- |
| `id` | Идентификатор пользователя в системе |
| `email` | Контактный email |
| `created_at` | Дата создания аккаунта |
| `updated_at` | Дата обновления |
| публичные поля профиля | Если они нужны приложению |

---

### Нельзя возвращать

| Данные | Почему нельзя |
| --- | --- |
| `password` | Пароль нельзя хранить и возвращать |
| `password_hash` | Может помочь при атаке на пароли |
| `password_salt` | Не нужен клиенту |
| `access_token` | В проекте токены передаются через cookies |
| `refresh_token` | Его нельзя отдавать в JSON |
| `token_hash` | Внутренние данные сервера |
| `client_secret` | Секрет OAuth-приложения |
| `reset_token` | Кроме учебного reset-flow для тестирования |
| `reset_token_hash` | Внутренние данные сервера |
| OAuth access token | Не должен попадать клиенту |
| внутренние OAuth-данные | Если они не нужны клиенту |

---

### В рамках проекта

Для ответа используется безопасная схема:

```text
UserResponse
```

Она возвращает только:

```text
id
email
created_at
updated_at
deleted_at
```

И не возвращает:

```text
password_hash
password_salt
tokens
token_hash
yandex_id
vk_id
```

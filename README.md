# Лабораторная работа №7 — MinIO Object Storage

## Описание проекта

Проект представляет собой REST API на FastAPI с авторизацией, MongoDB, Redis и объектным хранилищем MinIO.

В рамках лабораторной работы №7 реализовано хранение файлов через MinIO. Файлы не сохраняются в файловой системе приложения и не хранятся в MongoDB как BLOB. В базе данных сохраняются только метаданные файлов: оригинальное имя, размер, MIME-type, bucket, object key и владелец файла.

Также реализовано обновление профиля пользователя с возможностью установки аватара через `avatar_file_id`.

## Работа с файлами

### Загрузка файла

Файл загружается через endpoint:

```text
POST /files
```

Формат запроса:

```text
multipart/form-data
```

Поле файла:

```text
file
```

Разрешённые MIME-типы для аватара:

```text
image/png
image/jpeg
image/jpg
```

Максимальный размер файла задаётся переменной окружения:

```env
MAX_FILE_SIZE=10485760
```

По умолчанию — 10 MB.

После загрузки файл сохраняется в MinIO, а в MongoDB сохраняются только его метаданные.

Пример ответа:

```json
{
  "id": "b38a39f6-b47f-4ddb-8fc6-4bc3899193c9",
  "original_name": "avatar.png",
  "size": 1400000,
  "mimetype": "image/png",
  "url": "/files/b38a39f6-b47f-4ddb-8fc6-4bc3899193c9"
}
```

### Скачивание файла

```text
GET /files/{file_id}
```

Файл отдаётся потоком через `StreamingResponse`.

При скачивании устанавливаются заголовки:

```text
Content-Type
Content-Disposition
Content-Length
```

### Удаление файла

```text
DELETE /files/{file_id}
```

При удалении выполняется:

* soft delete записи в MongoDB;
* удаление объекта из MinIO;
* инвалидация Redis-кеша метаданных файла.

## Redis-кеширование

Для метаданных файлов используется Redis.

Ключ кеша:

```text
wp:files:{fileId}:meta
```

TTL:

```text
300 секунд
```

При первом скачивании файла метаданные берутся из MongoDB и сохраняются в Redis. При повторном запросе метаданные берутся из кеша. При удалении файла кеш инвалидируется.

## Контрольные вопросы

### 1. В чём фундаментальная разница между объектным хранилищем, файловой системой и базой данных для хранения файлов?

Файловая система хранит файлы как обычные файлы в папках на диске сервера, например `/uploads/avatar.png`. Такой подход простой, но плохо подходит для Docker и масштабирования: если приложение запущено в нескольких контейнерах, файл может оказаться только в одном из них.

База данных хранит структурированные данные. Теоретически файл можно сохранить в БД как BLOB, то есть как бинарные данные, но это увеличивает размер базы, усложняет резервное копирование и создаёт лишнюю нагрузку на БД.

Объектное хранилище, например MinIO, хранит файлы как объекты. Каждый объект имеет данные, ключ объекта и метаданные. Такой подход лучше подходит для файлов: сами файлы лежат в MinIO, а в MongoDB хранятся только метаданные и связи с пользователями.

В данном проекте используется именно такой подход: файл хранится в MinIO, а MongoDB хранит `File`-документ с `user_id`, `original_name`, `object_key`, `size`, `mimetype`, `bucket` и `deleted_at`.

---

### 2. Что такое Bucket в MinIO/S3 и как он соотносится с папками в файловой системе?

Bucket — это контейнер для хранения объектов в MinIO/S3. В проекте используется bucket:

```text
wp-labs-files
```

Bucket можно грубо сравнить с верхнеуровневой папкой, но технически это не обычная папка файловой системы. Внутри bucket файлы хранятся как объекты с уникальными ключами.

Например:

```text
bucket: wp-labs-files
object_key: 6a1981d54abc0f43fdadacc9/b38a39f6-b47f-4ddb-8fc6-4bc3899193c9-avatar.png
```

Здесь `wp-labs-files` — bucket, а длинная строка после него — object key. Символ `/` в object key визуально похож на папки, но для MinIO это часть имени объекта.

### 3. Почему рекомендуется использовать потоки (Streams) вместо буферов (Buffers) для загрузки файлов? В чём техническая разница?

Buffer — это когда файл сначала полностью загружается в оперативную память приложения, а потом уже отправляется дальше. Например, если файл весит 100 MB, приложение будет держать все 100 MB в RAM.

Stream — это потоковая обработка. Файл читается и передаётся частями. Например, backend может читать файл кусками по 32 KB и сразу отдавать эти части дальше.

Техническая разница:

```text
Buffer:
файл целиком → память приложения → MinIO

Stream:
часть файла → MinIO
часть файла → MinIO
часть файла → MinIO
```

В проекте поток используется при загрузке:

```python
file_stream=file.file
```

и при скачивании:

```python
StreamingResponse(
    file_stream.stream(32 * 1024),
    media_type=file_data["mimetype"],
    headers=headers,
)
```

Это позволяет не загружать весь файл целиком в память приложения.

---

### 4. Какие риски возникают при хранении файлов в базе данных (BLOB) по сравнению с объектным хранилищем?

При хранении файлов в БД как BLOB возникают следующие проблемы:

* база данных быстро увеличивается в размере;
* резервные копии становятся тяжелее;
* запросы к БД могут работать медленнее;
* БД начинает выполнять не только свою основную задачу хранения структурированных данных, но и роль файлового хранилища;
* сложнее отдавать большие файлы потоково;
* выше нагрузка на MongoDB.

Объектное хранилище лучше подходит для файлов, потому что оно специально предназначено для хранения бинарных объектов. В нашем проекте MinIO хранит сами файлы, а MongoDB хранит только метаданные.

### 5. Зачем хранить метаданные файлов в отдельной таблице/коллекции БД, а не полагаться только на метаданные MinIO?

MinIO хранит объект и техническую информацию о нём, но приложению нужны бизнес-данные:

* кто владелец файла;
* какое оригинальное имя было у файла;
* какой `file_id` используется в API;
* какой `object_key` соответствует файлу;
* какой MIME-type у файла;
* удалён файл или нет;
* можно ли текущему пользователю получить доступ к файлу.

Поэтому в MongoDB есть коллекция `files`, где хранится документ `File`.

Пример:

```json
{
  "id": "b38a39f6-b47f-4ddb-8fc6-4bc3899193c9",
  "user_id": "6a1981d54abc0f43fdadacc9",
  "original_name": "avatar.png",
  "object_key": "6a1981d54abc0f43fdadacc9/b38a39f6-b47f-4ddb-8fc6-4bc3899193c9-avatar.png",
  "size": 7140763,
  "mimetype": "image/png",
  "bucket": "wp-labs-files",
  "deleted_at": null
}
```

Это позволяет проверять права доступа, делать soft delete и связывать файл с пользователем или аватаром.

### 6. Как обеспечить безопасность загружаемых файлов?

В проекте безопасность загружаемых файлов обеспечивается несколькими способами.

Во-первых, endpoint `/files` доступен только авторизованному пользователю через `get_current_user`.

Во-вторых, проверяется MIME-type файла:

```python
ALLOWED_MIME_TYPES = {
    "image/png",
    "image/jpeg",
    "image/jpg",
}
```

Если тип файла не входит в разрешённый список, API возвращает ошибку.

В-третьих, проверяется максимальный размер файла:

```env
MAX_FILE_SIZE=10485760
```

Это 10 MB.

В-четвёртых, при скачивании, удалении и установке аватара проверяется владелец файла:

```python
File.user_id == str(current_user.id)
```

Также в реальном production-проекте можно добавить:

* проверку расширения файла;
* антивирусную проверку;
* проверку реального содержимого файла, а не только MIME-type;
* ограничение количества загрузок;
* хранение приватных файлов только за авторизованным API;
* аудит загрузок.

### 7. Что произойдёт, если файл будет загружен в MinIO, но запись в БД не удастся? Как обработать эту ситуацию?

Если файл загрузился в MinIO, но запись в MongoDB не создалась, возникает проблема: в MinIO остаётся объект, о котором приложение ничего не знает. Такой файл становится “мусорным”.

В проекте это обрабатывается через компенсационное удаление. В `POST /files` загрузка в MinIO и сохранение метаданных находятся в `try`. Если после загрузки возникает ошибка, backend пытается удалить объект из MinIO:

```python
except Exception as exc:
    try:
        storage_service.delete_file(object_key)
    except Exception:
        pass

    raise HTTPException(
        status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
        detail=f"File upload failed: {str(exc)}",
    )
```

То есть если MongoDB insert не удался, приложение пытается откатить загрузку и удалить файл из MinIO.

### 8. Как реализовать публичный доступ к некоторым файлам и приватный к другим?

Можно добавить в модель `File` поле, например:

```python
is_public: bool = False
```

Для приватных файлов backend должен работать как сейчас:

```text
клиент → FastAPI → проверка пользователя → MinIO → файл
```

То есть файл отдаётся только после проверки авторизации и владельца.

Для публичных файлов можно сделать отдельную логику:

```text
если is_public == True → файл можно получить без проверки владельца
если is_public == False → нужна авторизация и проверка owner
```

Также можно использовать presigned URL — временную ссылку на объект в MinIO. Тогда backend проверяет права и выдаёт ссылку, которая живёт ограниченное время.

В текущем проекте все файлы считаются приватными, потому что доступ к `/files/{file_id}` защищён через `get_current_user`.

### 9. Какие стратегии инвалидации кеша следует применять для метаданных файлов?

Кеш метаданных файла должен инвалидироваться, когда данные файла меняются или файл удаляется.

В проекте используется ключ:

```text
wp:files:{fileId}:meta
```

TTL:

```text
300 секунд
```

Стратегии инвалидации:

1. При удалении файла удалить кеш конкретного файла:

```python
cache_service.delete(file_meta_cache_key(file_id))
```

2. При изменении метаданных файла также удалить или обновить кеш.

3. При смене аватара можно инвалидировать кеш профиля пользователя.

4. Для списков файлов, если добавить `GET /files`, нужно удалять кеш списка при загрузке, удалении или изменении файла.

В проекте при `DELETE /files/{file_id}` кеш метаданных удаляется, поэтому следующий запрос не получит устаревшую информацию.

### 10. Что такое Presigned URL и когда его следует использовать вместо проксирования файлов через API?

Presigned URL — это временная подписанная ссылка на объект в MinIO/S3. Она позволяет клиенту загрузить или скачать файл напрямую из object storage без передачи файла через backend.

Обычный вариант в проекте:

```text
клиент → FastAPI → MinIO → FastAPI → клиент
```

Вариант с presigned URL:

```text
клиент → FastAPI
FastAPI проверяет права и выдаёт временную ссылку
клиент → MinIO напрямую
```

Presigned URL удобно использовать, когда:

* файлы большие;
* много скачиваний;
* нужно снизить нагрузку на backend;
* клиент может напрямую работать с object storage;
* ссылка должна жить ограниченное время.

В текущей лабораторной работе используется проксирование через API, потому что нужно показать авторизацию, проверку владельца, stream и правильные заголовки ответа.

### 11. Как отличается обработка больших файлов (> 100MB) от маленьких в контексте потоковой загрузки?

Для маленьких файлов разница между buffer и stream может быть не очень заметна, потому что файл занимает мало памяти.

Для больших файлов разница критическая. Если файл больше 100 MB и backend читает его в buffer, то каждый такой запрос будет занимать много оперативной памяти. При нескольких одновременных загрузках приложение может упасть из-за нехватки памяти.

При потоковой загрузке файл читается частями. Backend не держит весь файл в RAM, а передаёт его дальше постепенно.

Для больших файлов также полезно:

* использовать multipart upload;
* увеличивать таймауты;
* ограничивать максимальный размер файла;
* использовать presigned URL;
* отдавать файл через stream;
* не проксировать большие файлы через backend, если это не требуется;
* проверять размер до загрузки;
* хранить метаданные отдельно.
